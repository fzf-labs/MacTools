# Launcher implementation and acceptance

1. Remove the unpublished Calculator, File Search, Quicklinks, embedded clipboard/shortcut pages, content processing, and launcher starter pack. Preserve existing plugin data and clipboard consolidation.
2. Replace generic action ingestion with four explicit result kinds and a minimal optional declaration protocol. Review official legacy action IDs and feature workspace destinations; exclude configuration and unknown providers by default.
3. Extend shared application discovery with Finder, cryptex locations, additional directory/single-app scopes, asynchronous scans, directory observation, and manual refresh. Add the bounded macOS settings navigation inventory and explicit failure recovery.
4. Render a focused native search/list/action surface and independent General/Applications/System Settings/System Actions/Plugin Features settings. Preserve matching, stable identity, canonical execution, shortcut seeding, and portable personalization.
5. Verify changed tests first, then script/localization/changelog validation, complete CI, and the frozen PluginKit client. Rebuild the development app and inspect the actual desktop flows.

## Acceptance

Open with Option-Space, launch an application, open Wi-Fi settings, run a non-disruptive enabled-plugin operation, open the original Clipboard window, open a cleanup workspace, hide an entry in Launcher Settings, and confirm it disappears. Confirm plugin configuration is absent from results and disabling a plugin removes its entries without deleting favorites. Validate default shortcut conflicts and explicit clearing independently.

Inspect Chinese IME candidates, keyboard focus, native dialogs, multiple displays/Spaces, fullscreen behavior, accessibility, appearance preferences, and macOS 14 fallbacks. Automated key synthesis or a displayed shortcut binding does not establish physical global-shortcut delivery. Record only the desktop scenarios actually observed; do not mark unavailable physical checks as passed.

The earlier embedded-tool implementation's CI and screenshot evidence do not validate this revised scope. New evidence is recorded after the revised build and tests complete.

## Settings responsiveness follow-up

Runtime sampling while changing launcher pages found repeated calls to `LauncherSettingsView.entries` and `LauncherModel.catalogResults` from view rendering. Group construction recomputed the whole inventory, view initialization eagerly created discarded models and separate preference observers, and application-page entry requested a new scan. Native Form also created controls for large catalogs eagerly.

Launcher Settings now owns one lazily initialized state object across its five destinations. Source-specific snapshots are cached and invalidated after relevant host, application, or locale updates. Each render derives its groups once, favorites use a shared ID lookup, and native lists virtualize the application and action rows. Application-page entry uses the existing snapshot after first load; explicit refresh, scope changes, and filesystem observation continue to refresh discovery.

Focused snapshot, provider invalidation, warm application-cache, and launcher tests passed. The complete follow-up CI passed 3,128 cases with four opt-in cases skipped, plus all 239 script checks and the frozen PluginKit client. The Debug app was rebuilt and all five pages were exercised repeatedly. A second runtime sample no longer contained the original repeated settings getter/full-catalog path or an application scan during page switching. These samples include accessibility queries and are qualitative evidence, not a latency benchmark.

Cover metadata discovery, localization and identity, availability policy, cache invalidation, fallback, stale destinations, and asynchronous source updates with temporary fixtures.
