# Disk Cleanup

Disk Clean provides Junk Cleanup, Uninstall Apps, Installer Cleanup, Suspected App Leftovers, Project Cleanup, and Settings & Records in one workspace. Disk-usage visualization belongs to the separate Storage Explorer plugin; Disk Clean has no navigation to it.

## Review and removal

Application Uninstall loads the installed-app list automatically. Click an app to analyze its application, support, cache, preference, and sandbox files; the review selects that application and verified regenerable caches, while personal data stays off. Only one application can be selected for uninstall; switching applications or returning to search clears the prior selection. The installed-app inventory is automatic and requires no folder setup. Name and size sorting are shown directly in the toolbar. The fixed bottom bar summarizes the current application, and the final sheet reviews the selected categories before moving files to Trash.

All scans are read-only. Application inventory refreshes automatically; related-file analysis starts when an app is inspected or selected. Other cleanup scans remain explicit. Review ownership, source paths, measured size, consequences, and exclusions before selecting files. Ordinary cleanup and suspected leftovers require complete size measurements. Installed-app review can use a separate complete, identity-bound content inspection when size is unknown; unsupported volumes and incomplete safety inspections remain excluded. Default cache-retention rules apply to ordinary cleanup and suspected leftovers, not installed-app uninstall. Explicit user protection rules still apply to discovered paths and their resolved aliases.

Cleanup defaults to Trash. Moving items to Trash does not immediately free disk space, and the displayed size is an estimate. The existing permanent-delete option requires a second confirmation and does not apply to application uninstall or application leftovers. Interrupted staging in ordinary cleanup is reconciled before new cleanup is enabled; unresolved records remain visible in history. Installed-app removal delegates ephemeral file references to native Finder Trash operations, preserving the original name and allowing system authorization without changing directory permissions.

## Settings and records

Settings & Records shows cleanup history immediately, with operation summaries, searchable file details, and pinned recovery issues. Scan logs can be switched between cleanup workflows and cover the current session only. The deletion-mode setting applies to junk, installer, and project cleanup; app uninstall and app leftovers always use Trash.

## Applications and personal data

Application discovery always includes Applications folders and supplements them with available system-index and Launch Services results. Additional roots cannot remove the default locations. Inventory stops at app bundles and preserves separate copies; associated data is analyzed on demand. Both normal and system-index discoveries read version metadata, falling back to the build version. Missing list sizes are calculated in the background; missing metadata is labeled explicitly. Detail review shows discovered rows before inspection finishes, shares component discovery within an inventory epoch, and reuses size totals collected during content inspection. Third-party application bundles can move to Trash when their containing directory permits removal, including Homebrew installations and apps declaring managed installers. Bundled updaters and helpers move with the application bundle. Uninstall requests a graceful application exit; an explicit separate choice is required for force quitting. Native Finder Trash operations handle privileged removal and may display system authorization. System applications and MacTools itself remain excluded. Unreadable protected locations require access before their contents can be reviewed.

Application associations include exact Bundle IDs, ByHost preferences, web storage, updater/cache leaves, current-user Darwin caches, verified embedded component identities, metadata-attributed UUID containers, and explicit support-directory mappings. Ordinary name-matched files in an installed-app review are manually selectable, unselected personal-data candidates. The final confirmation lists selected candidates for ownership review, and execution rejects newly conflicting names. Known shared paths, ambiguous leftovers, protected content, and failed inspections remain excluded. Protected container metadata is inspected where Full Disk Access is available. Personal settings, support, and sandbox data are unselected by default. Verified regenerable cache paths are selected only after an explicit application selection. Per-category permission and incomplete-read states remain visible; missing size measurements are never treated as zero. System keychains, key material, saved passwords, shared containers, and ambiguous ownership remain protected. Explicitly selected, exclusively attributed application data may include its own cookies and session state; ordinary cache cleanup and suspected-leftover review keep the stricter default protection. Homebrew-owned applications use the same reviewed Trash flow; their package-manager installation records are retained, as noted in the confirmation. Background services required by a selected application bundle, or explicitly selected for cleanup, are eligible only when their configuration points inside the verified app, or to an explicitly declared helper with a matching team and signing requirement. The currently loaded job must match both its configuration path and program before it is stopped. System jobs request authorization. Only selected files move to Trash; stopping a required service does not implicitly select its configuration for deletion. Previously stopped processes are not automatically relaunched if the operation is cancelled. Unproven or shared services remain excluded; vendor uninstallers and Homebrew zap scripts are not executed.

An incomplete component check in an unrelated app does not block exact main-app associations backed by the installed application identity. Known conflicting claims still block removal. Same-team signed helpers inside the main Bundle ID namespace carry private-component evidence, including for metadata-attributed containers. Discovery and execution use the same ownership rules; unresolved ownership is reported against the affected file paths. Other component data and suspected leftovers continue to require complete ownership checks. Exact executable names can attribute only bounded, UUID-named force-quit timestamp records with no additional payload; changed contents or a newly installed executable-name claimant prevent removal.

Personal application data is never selected automatically. A scoped policy exception admits only the application’s own cookie/session state under reviewed support, web-storage, or metadata-owned container roots. It applies to exact app ownership and explicitly reviewed, bounded name candidates. Shared groups, system storage, saved passwords, key material, and explicitly user-protected files remain excluded. Execution reconstructs the same scope from frozen ownership evidence and reviews the contents again.

Application bundles move before associated data. Data is retained if a bundle move fails, another installed copy remains, ownership cannot be established, or presence checks are incomplete. Errors after a successful bundle move are reported per path as partial completion; remaining selected data stays available for fresh inspection and retry even after the bundle is gone. There is no cross-path atomic rollback. Refresh preserves the current app and selections for unchanged objects; replacing an object requires selecting it again. Application leftovers are suspected leftovers, not proof that an application no longer exists on any disconnected or unsearched volume. They are all unselected by default and checked again for reinstallation before removal.

## Product rules and coverage report

The app review's Scan Coverage action lists probed locations, their category and source, and whether each location was found, absent, denied, or incomplete. Search and the incomplete-only filter make gaps inspectable. Missing product adaptation and unfinished component ownership checks are explicit. This report describes location discovery; file-content checks and size completeness remain in the file review. Neither a successful probe nor Full Disk Access proves complete coverage of arbitrary application data.

The curated registry adds exact leaves and aliases for common editors, browsers, communication, design, and productivity apps. Chrome release channels and Code/Insiders retain separate directories. Firefox shared profiles, shared updaters, and editor extension roots remain review-only. Version/channel-stripped names and hidden `.config`, `.cache`, and `.local/share` candidates never authorize automatic selection. Installed-app candidates require individual selection and final ownership confirmation; suspected leftovers retain strict attribution checks. User vaults, models, arbitrary dot-directories, credentials, cloud data, and shared vendor roots are not inferred as disposable files.

ZCode support and updater-cache leaves are verified against its installed bundle metadata and the upstream [ZCode cask](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/z/zcode.rb). Its local CLI stores are not inferred from the app name.

Rules live in `DiskCleanApplicationProductRules.swift`. Research uses the upstream [Homebrew Cask registry](https://github.com/Homebrew/homebrew-cask/tree/master/Casks), including [Cursor](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/c/cursor.rb), [Chrome Beta](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/g/google-chrome@beta.rb), [Firefox](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/f/firefox.rb), and [Obsidian](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/o/obsidian.rb). Cask scripts are never executed. Adding a rule requires an exact supported Bundle ID, documented leaf paths, explicit personal/shared-data semantics, and temporary-fixture safety checks. Wildcards and vendor-root rules are rejected; curated ownership evidence is checked again before removal.

## Installers and projects

Installer scans prioritize Downloads, Desktop, and Documents, then search other ordinary folders in the current user’s home without folder setup. Discovery is limited to six directory levels, 60,000 entries, 5,000 candidates, and 30 seconds; reaching a limit is reported separately from empty results. Hidden folders, Library, Applications, application bundles, development dependencies, known cloud folders, symbolic links, aliases, and external or other mounted volumes are excluded. Results appear during discovery and show their source folders. Only old installer packages and XIP files under Downloads are selected by default; other locations, recent files, ZIPs, and uncertain disk images require explicit selection. Ordinary ZIP archives are excluded; installer ZIPs must pass bounded metadata inspection without extraction. Cloud placeholders are not downloaded for inspection. Inaccessible folders are reported, and execution retains the existing safety checks and identity-bound validation.

Project discovery searches ordinary local folders under the current user’s home for manifest files such as package.json, Cargo.toml, Package.swift, pyproject.toml, Gradle, Flutter, Composer, and .NET project files. Folder names do not determine coverage, and no folder setup is required. Home and top-level personal folders never become project cleanup roots. Library, Applications, hidden folders, application packages, dependency and build trees, known cloud folders, placeholders, links, and external or other mounted volumes are excluded from project discovery. The manifest search is bounded to eight directory levels, 60,000 entries, 100 projects, and 15 seconds. Each discovered project then uses the existing six-level artifact discovery, with a shared 60-second inspection deadline, 20,000 discovery entries per project, and 1,000 candidates. Limits and access failures are reported separately from empty results; checked projects appear progressively with their source paths. Nested projects preserve their enclosing repository’s Git state, and Git inspection disables repository-configured helpers. Supported artifacts include Node.js, Next.js, Nuxt, Rust, SwiftPM, Python, Gradle, Flutter, .NET, and Composer outputs. Git-tracked content, nested repositories, deployment keys, protected descendants, unknown inspections, and active build processes prevent unsafe removal. Recently active artifacts and projects with local or unpushed changes are not preselected.

## Permissions and limitations

Full Disk Access improves coverage of protected user data; it does not grant administrator privileges or remove shared-data safeguards. Denied locations and incomplete scans are shown separately from empty results. Roots, application events, and filesystem changes invalidate relevant reviews, and execution performs fresh checks. No cleanup is scheduled or performed automatically.

## Mole reference

The automatic inventory and five-category refinement was researched against [Mole commit 08c229bc5935610f81e43a33fc9a3d6dda72139e](https://github.com/tw93/Mole/tree/08c229bc5935610f81e43a33fc9a3d6dda72139e). Its scope and upstream source mapping are recorded in the [final uninstall specification](../superpowers/specs/2026-10-30-app-uninstall-final.md). Shared App Groups and common runtime/updater identities stay review-only, and MacTools does not execute Homebrew zap scripts; only selected services with verified app attribution and matching loaded-job metadata can be stopped.

This native Swift implementation was researched against [Mole commit 27ac801360d2fe61dd964d041cde71b9dac3c188](https://github.com/tw93/Mole/tree/27ac801360d2fe61dd964d041cde71b9dac3c188), including its CLI uninstall workflow. Mole is not bundled or executed as a backend, and the proprietary Mole native application is not part of this work.

| Reference | Decision | MacTools behavior |
| --- | --- | --- |
| `lib/clean/user.sh`, `lib/clean/dev.sh` | Retained/adapted behavior | Existing cache categories remain; exact reverse-DNS cache owners and unknown process results receive execution guards. Credentials and user identity remain excluded. |
| `lib/clean/project.sh`, `lib/clean/purge_shared.sh` | Adapted behavior | Explicit project markers, protected contents, recent activity, and tracked-file checks; existing target IDs and default-to-Trash semantics remain. |
| `bin/installer.sh` | Adapted behavior | Metadata-only ZIP identification, package formats, source roots, and live identity checks. Bounded home-folder discovery excludes cloud folders, application internals, dependencies, and linked or external locations. |
| `bin/uninstall.sh`, `lib/uninstall/batch.sh`, `lib/uninstall/review.sh` | Adapted behavior | Single-application review, per-path personal-data choices, multiple-copy protection, application-first ordering, and partial results. Verified service stopping and native authorized Trash are supported; arbitrary service mutation and unverified privileged components are excluded. |
| `lib/clean/apps.sh` | Adapted behavior | Exact application attribution and fresh installed-evidence checks. Incomplete inventories cannot authorize associated-data removal. |
| `SECURITY.md`, `SECURITY_AUDIT.md` | Research reference | Existing MacTools validated plans, no-follow identity checks, whitelists, sensitive-path protection, journaling, and recovery remain the deletion boundary. |

The implementation uses independently authored Swift services rather than copied shell code. See `LICENSING.md` for the distinction between research references and distributed third-party components. Any future direct code adaptation must retain the corresponding notices.
